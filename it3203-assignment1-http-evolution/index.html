HTTP: The Protocol That Carries the Web

IT 3203 Assignment 1: Research and Learn Web Evolution

Prepared by Nasir Hassan — Fall 2026

Executive overview

This report studies HTTP, the Hypertext Transfer Protocol, as one technical component of the World Wide Web. HTTP matters because it is the request-and-response language used when browsers, servers, mobile apps, APIs, and content delivery networks exchange web data.

The main finding is that HTTP has evolved from a one-line request in HTTP/0.9 into a layered modern system that supports headers, status codes, caching, cookies, security policies, APIs, streaming, multiplexing, TLS encryption, and QUIC-based HTTP/3. The core purpose remains the same: a client asks for a resource, and a server responds.

Research scope and learning goals

Selected web component

The chosen topic is HTTP because it connects browsers, servers, URLs, web pages, APIs, cookies, caching, security, and performance.

Learning goal

A high school student should be able to explain what HTTP does, how it changed over time, and why modern sites use HTTPS, HTTP/2, and HTTP/3.

Main idea

HTTP is not a website, browser, or server. It is the communication rule set that lets those systems understand one another.

Where HTTP fits in a web request

When a user types a URL, the browser identifies the site, opens a connection, sends an HTTP request, receives an HTTP response, and renders the returned content. The page may require many additional HTTP requests for images, CSS, JavaScript, fonts, videos, and data.

StepWhat happens
1. User enters a URLThe browser identifies the scheme, host, and resource path.
2. Browser connectsDNS, TCP or QUIC, and TLS prepare a secure path to the server.
3. HTTP requestThe browser sends a method, path, headers, and sometimes a body.
4. HTTP responseThe server returns a status code, headers, and content or data.

HTTP as a request and response conversation

HTTP works like a structured conversation. A request says what the client wants; a response tells whether the server could provide it and includes the data or an error explanation.

Request

Example: GET /index.html HTTP/1.1. The browser asks for a resource and adds headers such as Host, Accept, and User-Agent.

Response

Example: HTTP/1.1 200 OK. The server sends status information, headers such as Content-Type, and the requested body.

Message parts that make HTTP useful

Methods

GET, POST, PUT, PATCH, and DELETE describe the action the client wants.

Status codes

Codes such as 200, 301, 404, and 500 provide quick results that software can understand.

Headers

Headers carry metadata about content type, compression, cookies, caching, authentication, and security.

Body

The body carries HTML, JSON, images, files, or form data when a message needs content.

Origin story and major milestones

1989–1991: Tim Berners-Lee and colleagues at CERN develop the early World Wide Web pieces: HTML, HTTP, a browser, and a web server.
1991: HTTP/0.9 uses a one-line GET request and returns a hypertext document.
1996: HTTP/1.0 documents status codes, headers, and multiple content types.
1997–1999: HTTP/1.1 improves persistent connections, virtual hosting, caching, compression, and chunked transfer.
2015: HTTP/2 introduces binary framing, multiplexing, and header compression.
2022: The modern HTTP RFC set updates shared semantics, HTTP/1.1, HTTP/2, and HTTP/3.

HTTP/0.9: the one-line protocol

HTTP/0.9 was extremely simple. A client sent a line such as GET /mypage.html, and the server returned the document. There were no status codes, no headers, no content negotiation, and no official way to describe non-HTML files. This matched the early web because the goal was only to retrieve hypertext documents.

HTTP/1.0 and HTTP/1.1

HTTP/1.0 made the protocol more practical by adding protocol versioning, status codes, headers, and support for different media types. HTTP/1.1 then improved performance and reliability through persistent connections, virtual hosting with the Host header, better caching, compression, range requests, and chunked transfer encoding.

HTTP/1.1 became durable because it balanced simplicity, compatibility, and enough features for commercial web growth.

Security: HTTPS changed expectations

HTTP originally sent data in clear text. HTTPS adds TLS so the browser can authenticate the site and encrypt traffic. This is essential for passwords, payment information, private messages, cookies, and forms. Today, browsers treat HTTPS as the normal expectation for trustworthy sites.

HTTP as a platform for applications

Modern web applications depend on HTTP for APIs and real-time features. REST APIs use HTTP methods and status codes. JSON bodies carry structured data. WebSocket and Server-Sent Events extend web communication beyond simple document loading.

HTTP/2: performance redesign

HTTP/2 keeps the same meanings as HTTP/1.1 but changes the wire format. It uses binary frames and multiplexed streams so several requests can share one connection at the same time. Header compression reduces repeated metadata. These changes target the performance problems created by pages that require many resources.

HTTP/3 and QUIC

HTTP/3 keeps HTTP semantics but runs over QUIC instead of TCP. QUIC is a secure transport over UDP. It supports multiplexing, encryption, and connection migration, which can be helpful for mobile devices that move between networks. HTTP/3 was designed to reduce transport-level head-of-line blocking that can hurt HTTP/2 over TCP.

Current status

In 2026, the web is mixed. HTTP/1.1 remains important for compatibility, HTTP/2 is common for production websites, and HTTP/3 continues to grow through browser, server, and CDN support. Adoption statistics vary by measurement method, because supporting a protocol is not the same as measuring the share of actual user traffic.

People and organizations

CERN and Tim Berners-Lee

HTTP began as part of the early World Wide Web work at CERN.

IETF HTTP Working Group

The IETF standardizes HTTP through RFCs and ongoing working-group discussions.

Browser vendors

Browser teams implement protocol negotiation, security behavior, caching, and compatibility.

CDNs and cloud providers

Large edge networks help deploy HTTP/2 and HTTP/3 globally.

Future directions

Future HTTP work is likely to focus on stronger privacy, simpler deployment, better prioritization, improved browser performance, QUIC growth, and compatibility across enterprise networks. HTTP will remain important because it sits under web pages, APIs, mobile apps, authentication systems, e-commerce, streaming, and cloud services.

Conclusion

HTTP is the web's durable coordination layer. It changed from a tiny hypertext retrieval tool into a full protocol family for secure, high-performance, application-driven communication. The reason HTTP survived is that it kept its basic request-response model while adding the features needed for modern web life.
